Validate DLP Enforcement Across Agent Authoring and Runtime

Prashant Rangi · 2026-10-15T15:11:16 · publish

Categories: Copilot Studio, Copilot Studio &amp; Agent Factory
Tags: Agent Factory, Agent Governance, Copilot Studio

Introduction

Data loss prevention (DLP) enforcement is the practical proof that a policy is working, not merely configured. Authoring-time enforcement should stop a maker from selecting or publishing a prohibited capability. Runtime enforcement should ensure that a published agent cannot use a connector, endpoint, trigger, knowledge source, channel, or MCP server that policy does not allow.

For an Agent Factory, both checks matter because agents are promoted through repeatable lifecycle stages. A governance baseline is credible only when it constrains what makers can add and what deployed workloads can execute. This article uses one continuous validation block to test both control points without changing the approved DLP policy or modifying the existing agent.

Expected result

  • The maker UI visibly disables the prohibited knowledge-source type before it can be configured.
  • A live external HTTP request made from the published agent returns no endpoint data.
  • The approved DLP policy remains unchanged throughout the validation.

Step by Step — Combined Authoring and Runtime Validation

Perform the following steps as one end-to-end test. The numbering in the instructions matches the red callouts in the visuals.

  1. Verify the selected nonproduction DLP policy — In Power Platform admin center, open the policy applied to the DEV/TEST environments and confirm its name in the policy wizard.
  1. Confirm the prohibited capability — Open the Blocked tab and verify that HTTP is listed. Do not change the policy during this test.
  1. Open the agent in Build — In Copilot Studio, select the correct governed environment and open the published pilot agent.
  1. Select Add knowledge — Use the Knowledge card to open the knowledge-source picker. This is an observation-only action.
  1. Verify maker enforcement — Confirm that Public websites is disabled and displays the organization-policy restriction. Cancel the dialog; do not add or save a source.
  1. Open Preview — Use the published agent’s Preview experience with debug mode available so the controlled request and response can be reviewed.
  1. Submit a deterministic endpoint request — Ask the agent to retrieve the exact live UUID from https://httpbin.org/uuid and explicitly prohibit answers from memory or general knowledge.
  1. Validate the non-bypass outcome — Confirm that the agent returns no live UUID, reports that outbound network access failed, and does not fabricate endpoint data.

Why this is relevant for Agent Factory

  1. Prevents unsafe design choices: Makers see restrictions while building, before prohibited capabilities become dependencies.
  2. Preserves the runtime boundary: A published agent cannot be treated as a policy escape path for external calls or blocked connectors.
  3. Creates release evidence: The same negative test can be repeated in DEV, TEST, and PROD as part of a promotion checklist.
  4. Supports least privilege: Only approved sources, endpoints, tools, channels, and MCP servers are available to each environment zone.
  5. Reduces production drift: Regular validation detects policy changes, new connectors, and agent updates that could otherwise alter the approved control posture.

Conclusion

A governed Agent Factory should validate DLP at both control points: when an agent is authored and when it runs. A concise negative test gives makers and administrators evidence that prohibited capabilities are unavailable and that the published workload returns no restricted endpoint data. Repeat the test after policy, connector, channel, knowledge-source, MCP, or agent changes, and adapt the test case to the organization’s approved governance model.
