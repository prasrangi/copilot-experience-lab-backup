Govern the Agent Factory Lifecycle with Power Platform Environment Groups

Sagar Rangi · 2026-10-11T16:44:10 · publish

Categories: Copilot Studio, Copilot Studio &amp; Agent Factory, Power Platform ALM
Tags: Agent Factory, Agent Governance, Copilot Studio

A working deployment pipeline answers one question: can the agent solution move from DEV through TEST to PROD? It does not decide who can edit an agent, which AI features are allowed, or whether someone can bypass the pipeline with an unmanaged change.

This next part of the Agent Factory lab puts those controls around the environments. Power Platform environment groups let us manage lifecycle rules centrally, with room for development collaboration and tighter controls downstream.

Complete these two runbooks first, in order:

  1. Part 1: Building an Agent Factory Pilot — From Copilot Studio Draft to Power Platform Pipeline. Create the draft agent, solution, pipeline host, environment records, and deployment stages.
  2. Part 2: Deploy and Promote the Pilot Agent Through the Power Platform Pipeline. Validate the managed solution deployment into TEST and promotion to PROD.

This article assumes those resources already exist. It adds governance to that lifecycle; it does not recreate the agent or deployment pipeline.

What changes in this part?

The lab uses three lifecycle groups. Each environment goes into the group that matches its job:

Environment group Environment Purpose
AF-LIFECYCLE-DEVELOPMENT AF-PILOT-DEV Agent development and controlled maker collaboration
AF-LIFECYCLE-TEST AF-PILOT-TEST Validation and acceptance testing under downstream controls
AF-LIFECYCLE-PRODUCTION AF-PILOT-PROD Production-oriented governance for the pilot

In this walkthrough

  1. Check the lifecycle groups
  2. Configure rules and add environments
  3. Keep development flexible, but controlled
  4. Protect the TEST environment
  5. Apply production-oriented controls
  6. Validate the effective governance
1. Check the lifecycle groups before creating anything

Open Power Platform admin center > Manage > Environment groups

If the environment groups do not exist, create them using the steps below
  1. Open Power Platform admin center and select Manage > Environment groups.
  2. Select New group.
  3. Enter the lifecycle group name and a description that explains its purpose.
  4. Select Save and repeat for the other lifecycle groups that do not already exist.
2. Configure the rules, then add each environment

Configure the destination group’s rules before changing environment membership. That makes the policy that will take effect visible before the environment is added.

  1. Open Manage > Environment groups and select the destination group.
  2. Open Rules and select Add rules.
  3. Select the required rules, configure their values, and save each one.
  4. Select Apply changes and wait for confirmation.
  5. Open the group’s Environments tab and select Add environments.
  6. Search for the exact environment name. Check its type, region, Dataverse status, Managed status, and current group before selecting it.
  7. Select Add environments. If prompted, enable Managed Environments after reviewing the implications.
  8. Wait for processing to finish before checking the result.

Repeat for DEV, TEST, and PROD using the mapping above.

3. Keep development flexible, but controlled

AF-LIFECYCLE-DEVELOPMENT is where makers build and change the agent.

AF-PILOT-DEV — Rules

  • Backup retention: Effective retention: seven days, because DEV is Sandbox-type
  • Default deployment pipeline: Host: AF-PILOT-HOST; pipeline: AF-PILOT-Standard-Release
  • Generative AI settings: Existing approved/default configuration retained
  • Agent sharing with Editor permissions: Enabled for development collaboration
  • Agent sharing with Viewer permissions: Enabled
  • Solution checker enforcement: Warn
  • Usage insights: Enabled
4. Protect TEST from direct changes

AF-LIFECYCLE-TEST should validate what the pipeline delivered.

AF-PILOT-TEST — Rules

  • Conversation transcript access: Rule applied with its default configuration; review access and retention against the privacy policy before real user testing
  • AI prompts: Enabled using the rule’s default configuration
  • Authentication for agents: Microsoft Entra authentication required
  • Backup retention: Seven days, because TEST is Sandbox-type
  • Generative AI settings: Existing approved/default configuration retained
  • Preview and experimental AI models: Disabled
  • Agent sharing with Editor permissions: Disabled
  • Agent sharing with Viewer permissions: Enabled; individuals and security groups permitted, with no numerical viewer limit imposed
  • Sharing solution-aware cloud flows: Maker sharing disabled
  • Solution checker enforcement: Block; imports containing critical violations are blocked
  • Unmanaged customizations: Blocked; change the agent in DEV and promote it through the pipeline
  • Usage insights: Enabled using the rule’s default configuration

Solution Checker Block mode is not an overall security certification. Review which violations it blocks, inspect results, and retain the deployment checks from Part 2. Authentication, sharing, and transcript access need their own validation.

5. Apply production-oriented controls without overstating readiness

AF-LIFECYCLE-PRODUCTION records the stricter downstream baseline.

AF-PILOT-PROD — Rules

  • Conversation transcript access: Rule applied with default configuration; for real production, restrict visibility to approved support and compliance roles
  • AI prompts: Enabled using the rule’s default configuration
  • Authentication for agents: Microsoft Entra authentication required
  • Backup retention: Currently seven days because AF-PILOT-PROD is Sandbox-type; a Production-type Managed Environment can support longer retention, subject to applicable limits
  • Generative AI settings: Existing approved/default configuration retained
  • Preview and experimental AI models: Disabled
  • Agent sharing with Editor permissions: Disabled
  • Agent sharing with Viewer permissions: Enabled; individuals and security groups permitted. Use a controlled pilot-user security group
  • Sharing solution-aware cloud flows: Maker sharing disabled
  • Solution checker enforcement: Block
  • Unmanaged customizations: Blocked
  • Usage insights: Enabled using the rule’s default configuration

 

Summary: What We Achieved and How It Supports an Agent Factory

Across this guide and the two earlier runbooks, the pilot now has an agent, a validated DEV-to-TEST-to-PROD deployment path, and a lifecycle governance baseline. Environment groups add consistent controls around that release process rather than leaving each environment to be managed independently.

What we achieved

  • Separated the lifecycle: Defined DEVELOPMENT, TEST, and PRODUCTION groups for the corresponding pilot environments, with different responsibilities for building, validating, and operating agents.
  • Established the DEV baseline: Recorded seven configured rules covering backups, the default deployment pipeline, generative AI settings, editor and viewer sharing, Solution Checker in Warn mode, and usage insights.
  • Strengthened the downstream baseline: Recorded twelve rules for both TEST and PROD, including Microsoft Entra authentication, disabled experimental AI models, tighter sharing controls, blocked unmanaged customizations, and Solution Checker in Block mode.
  • Connected governance to delivery: Linked the development baseline to AF-PILOT-HOST and AF-PILOT-Standard-Release, keeping agent changes aligned with the deployment process established in Parts 1 and 2.

How this helps build an Agent Factory

An Agent Factory needs a repeatable way to build and release agents without recreating governance for every project. These lifecycle groups provide a starting point: makers work within the development baseline, downstream environments use stricter controls, and additional eligible environments can adopt the relevant published group rules after review.

Centralizing those rules reduces manual configuration drift and gives platform owners a clearer place to maintain lifecycle policy. Combined with the solution and pipeline, the setup creates a reusable foundation for onboarding more agent projects while keeping development, validation, and release responsibilities distinct.

This is a governed pilot foundation, not a production-readiness certification. Existing access assignments, transcript privacy, effective permissions, and agent evaluation still require validation. The current PROD pilot is Sandbox-type with seven-day backup retention; production deployment and publication need their own approved decisions.
