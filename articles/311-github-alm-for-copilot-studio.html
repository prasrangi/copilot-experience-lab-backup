Agent Factory ALM with GitHub Actions

Sagar Rangi · 2026-10-19T16:23:52 · publish

Categories: Copilot Studio, Copilot Studio &amp; Agent Factory, Power Platform ALM
Tags: Agent Factory, Copilot Studio, Deployment Pipelines, Power Platform ALM

Introduction

Application lifecycle management gives agent changes a repeatable route from development to testing and release. GitHub Actions can automate Power Platform solution export and import while keeping the workflow definition and deployment evidence together.

For an Agent Factory, that route helps teams apply a consistent release process as the number of agents grows. OpenID Connect lets a workflow authenticate with short-lived tokens instead of storing a client secret in GitHub.

Lab scope

In this walkthrough, we added GitHub ALM to the existing AF-PILOT-DEV, AF-PILOT-TEST and AF-PILOT-PROD lab environments. We kept Power Platform Pipelines and Azure DevOps unchanged, and gave the new GitHub components a GIT suffix.

Before starting

  • Use an existing solution in DEV and confirm access to all three Dataverse environments. This example deploys AF_Pilot_Agent.
  • You need GitHub repository administration, permission to register an Entra application and permission to manage application users in each target.

Step by Step

Step 1 Create a dedicated repository

At github.com/new, choose the owner, enter AF-PILOT-ALM-GIT, select Private and enable README. Create the repository so the new workflow has its own version history without changing the existing ALM routes.

Step 2 Create GitHub deployment environments

Open Settings > Environments > New environment. Create AF-PILOT-DEV-GIT, AF-PILOT-TEST-GIT and AF-PILOT-PROD-GIT. These are GitHub job contexts for variables and deployment controls; they do not create new Power Platform environments.

Step 3 Restrict deployments to main

In each GitHub environment, choose Selected branches and tags. Add a Branch rule with the exact pattern main and verify it is saved. This limits eligible source branches; it is not an approval gate.

Step 4 Register the GitHub automation application

In Microsoft Entra ID admin center, open App registrations > New registration. Create APP-AF-GitHub-ALM-GIT as single tenant and leave Redirect URI blank. Record its Application client ID and Directory tenant ID.

Step 5 Confirm the GitHub OIDC subject

Open repository Settings > Actions > OIDC. Copy the actual subject prefix before configuring Entra trust. This repository uses immutable owner and repository IDs, so a name-only subject would not match its token.

Observed prefix: repo:prasrangi@16495131/AF-PILOT-ALM-GIT@1425265240

Step 6 Add the federated credentials

In the app, open Certificates and secrets > Federated credentials > Add credential. Use GitHub Actions deploying Azure resources, enter the owner and repository IDs, select Environment and enter the matching GIT environment name.

Step 6 Verify all three trusts

Create FIC-AF-DEV-GIT, FIC-AF-TEST-GIT and FIC-AF-PROD-GIT manually. Each subject is the verified prefix followed by :environment: and its GIT environment name. Repository creation does not create these Entra credentials automatically.

Issuer: https://token.actions.githubusercontent.com. Audience: api://AzureADTokenExchange. No client secret or certificate was created.

Step 7 Add the application user in each environment

In Power Platform admin center, open the existing DEV environment > Settings > Users + permissions > Application users > New app user. Select Add an app and find APP-AF-GitHub-ALM-GIT using its exact client ID.

Step 7 Assign roles and repeat for TEST and PROD

Select Security roles, assign System Administrator for this lab and save the role selection. Confirm the additional role-assignment Save if prompted, then create the application user. Repeat in TEST and PROD with each environment’s own root business unit.

System Administrator is broad lab access, not a least-privilege claim. Review solution requirements and identity separation before adapting this pattern to a real production service.

Step 8 Configure the GitHub environment variables

In each GitHub environment, select Add environment variable and create PP_CLIENT_ID_GIT, PP_TENANT_ID_GIT and PP_ENVIRONMENT_URL_GIT. Use the app overview for IDs and Power Platform environment details for the Dataverse URL.

Step 9 Validate passwordless connections

Open Actions and configure a new workflow. Save af-pilot-oidc-validate-GIT.yml under .github/workflows, review the code and commit it. Run AF-PILOT-OIDC-Validate-GIT on main to check each environment without exporting or importing a solution.

Read the tested connectivity YAML

Step 9 Confirm the connection results

The connectivity run succeeded for DEV, TEST and PROD. Each job authenticated through workload identity federation and connected to its configured Dataverse target. This checks authentication and access, not agent behavior.

Open connectivity run 39233091469

Step 10 Create the solution release workflow

Add .github/workflows/af-pilot-solution-release-GIT.yaml. Unlike the connection test, this workflow exports AF_Pilot_Agent as managed, stores the package and imports it into TEST. PROD is optional and depends on successful TEST import.

Read the tested release YAML

Step 11 Run DEV export and TEST import first

In Actions, select AF-PILOT-Solution-Release-GIT > Run workflow and choose main. Leave deploy_prod unchecked and the confirmation blank. The workflow exports version 1.0.1.2 and checks the package fingerprint before TEST import.

Step 12 Validate the solution in Copilot Studio

Switch to AF-PILOT-TEST in Copilot Studio, open Solutions and select Managed. Confirm AF Pilot Agent version 1.0.1.2, then open its agent. The existing name AF-PILOT-DEV-Assistant is retained across environments.

Step 13 Run the optional PROD deployment

After reviewing TEST, start a new release run on main, enable deploy_prod and enter DEPLOY-TO-PROD exactly. This run re-exports DEV; its TEST and PROD jobs download the same artifact by ID and verify its inner package SHA-256.

If PROD is selected, it follows TEST import automatically. This lab has no independent reviewer gate, and the confirmation text is not a substitute for one.

Validation

Full solution deployment passed in run 39263935638 in 3 minutes 26 seconds. The DEV, TEST and PROD summaries recorded the same inner managed-package fingerprint for version 1.0.1.2.

The recorded result is end-to-end solution export and import. The workflow does not publish the Copilot Studio agent or configure channels. TEST Review still showed no evaluation run and no channel configured; published runtime and end-user access have not been validated.

Why this is relevant for Agent Factory

A shared release pattern makes it easier to apply the same deployment checks to multiple agents. Workflow history identifies the code and run used, while managed packages and matching fingerprints make promotion traceable.

Passwordless authentication removes a stored client secret from this route. GitHub environments separate target settings, but the shared application in this lab still has permissions across all three Dataverse environments.

Before adapting this for production

  • Add independent approval and protect workflow changes through branch rules and code review. Confirm the GitHub plan supports the required controls for private repositories.
  • Separate production deployment identities where appropriate, review roles and pin reviewed action revisions.
  • Add solution checks, representative agent evaluations, approved channel tests and an explicit publication decision.
  • Define recovery and rollback procedures. Solution import success is not proof that a release is safe for users.

Conclusion

GitHub Actions provides a repeatable ALM route for Copilot Studio solutions using managed packages and passwordless authentication. Its deployment evidence supports release review, while approvals, publication and runtime tests complete the production process. An Agent Factory can reuse this pattern without treating a green import as proof of a fully validated agent.
